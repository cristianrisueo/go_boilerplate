# Claude Code configuration

Claude writes the code. This configuration decides three things:
**what Claude knows**, **what Claude cannot do**, and **how its work is
checked**. Every file covers one of those three, or helps you get started.

This README is for people. Claude Code does not load it.

## Requirements

### Documents

The configuration expects these documents, at these exact paths and with
the structure of their templates. The skills, permissions and hooks refer
to them.

| Document                    | Purpose                                                       | Written by                                                     | Follows                              |
| --------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------ |
| `docs/project-specs.md`     | What the service does and how it is built. Immutable.         | The architect: by hand from the template, or `/design-project` | `.claude/templates/project-specs.md` |
| `docs/sprints-plan.md`      | How each sprint is executed, audited and verified. Immutable. | `/scaffold-project`                                            | `.claude/templates/sprints-plan.md`  |
| `docs/reports/sprint-NN.md` | What each sprint delivered and how it was audited.            | `/start-sprint` and `/audit-sprint`                            | `.claude/templates/sprint-report.md` |
| `docs/sprints-debt.md`      | What each audit leaves behind as non-blocking debt.           | `/scaffold-project`, then `/audit-sprint`                      | `.claude/templates/sprints-debt.md`  |

The specs are the only document written by hand. There are two routes to
them, and they end in the same place:

1. Write them in a chat with any model, following
   `.claude/templates/project-specs.md`, and paste the result into
   `docs/project-specs.md`.
2. Run `/design-project` in an architect session and argue the design out
   with it.

Everything downstream is then generated by `/scaffold-project` from those
specs: the sprint plan, the debt ledger, `docs/reports/`, the "Project
rules" section of `CLAUDE.md` and the project requirement of
`.claude/rules/repository.md`. Nothing else derives the plan, and nothing
edits the specs during a sprint.

The four templates live in `.claude/templates/`. `project-specs.md` is the
contract `/scaffold-project` reads, so a section missing from the specs is a
section the generator cannot use. Editing any template takes a plain `claude`
developer session: `.claude/` is the agent configuration, and
`hooks/guard.sh` blocks every role — including the architect, which may
write `CLAUDE.md` and `.claude/rules/` but never the templates, permissions,
hooks, launchers or skills.

### What the configuration relies on

The configuration cites sections by number and reads headings by name.
**Never remove, rename or renumber them.** If a section does not apply,
write `Not applicable.` inside it.

| Element                                                         | Used by                                                                                                                               |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Specs §5 Invariants                                             | `go-reviewer`, audit check A6, "Project rules" in `CLAUDE.md`                                                                         |
| Specs §6.1 Response format and §6.3 Error catalogue             | `CLAUDE.md`, audit check A5, test rule T4                                                                                             |
| Specs §7 Tech stack                                             | Scope rule: no dependency outside this list                                                                                           |
| Specs §9 Directory structure                                    | Audit check A8                                                                                                                        |
| Specs §12.3 Makefile targets                                    | `stop-tests.sh`, `guard.sh`, `CLAUDE.md` and both sprint skills (`check`, `test-short`, `test`, `up`, `down`, `reset`, `migrate-new`) |
| Specs §1, §5, §6.2, §6.3, §7, §8.2, §9, §12.3, §13.3            | `/scaffold-project`: it generates from them, so none of them may say `Not applicable.`                                                |

### Tools

The hooks need `bash`, `git`, `jq` and `go` installed locally.

## 1. What Claude knows

Everything in this section is **advisory**: Claude reads it and tries to
follow it, but nothing forces it to.

### `CLAUDE.md` (project root)

- **What it does:** the first thing Claude reads in every session. It points
  to the specs and the plan, names the four roles and their launchers, lists
  the commands to use, and describes how Go is written in this project.
- **Why:** without it, Claude guesses the conventions and every session
  starts from zero.
- **Worth it?** Yes, essential. Its "Project rules" section is what each
  project fills in, and `/scaffold-project` writes it from specs §5. The
  audit and `go-reviewer` treat a breach of those rules as blocking.

### `rules/repository.md`

- **What it does:** instructions that are loaded only when Claude works on
  the code that talks to the database (`internal/**/repository.go` and its
  tests).
- **Why:** the data layer is where an agent makes the most expensive
  mistakes (unsafe SQL, a missing access filter). These instructions should
  not take up context while Claude works on other layers. Its "Project
  requirement" is filled in for each project, from specs §5.
- **Worth it?** Yes. Almost every Go backend has a database, and this is the
  only rule we keep.

### `skills/postgres-migrations/SKILL.md`

- **What it does:** explains how to create and test a change to the database
  structure. Claude loads it on its own, only when it needs it.
- **Why:** a bad migration cannot be undone in production. Claude should
  always follow the same procedure.
- **Worth it?** Yes, but it is the least reliable piece: it depends on
  Claude deciding to load it. If it does not, invoke it by hand with
  `/postgres-migrations`.

## 2. What Claude cannot do

Everything in this section is **enforced**: Claude Code applies it, not the
model.

### `settings.json`

- **What it does:** rules for every session, whatever the role. It forbids
  `git push` and `git merge`, prevents disabling the permission system, and
  asks for approval before a `Write` to the specs or the plan — a `Write` is
  a whole-file overwrite, which is never what a correction to an immutable
  document looks like. It also connects the hooks.
- **Why:** these are the project's red lines. They must apply to everyone,
  always.
- **Worth it?** Yes, essential. Note where the line moved: the specs and the
  plan are no longer protected by an `ask` on `Edit`, which every role could
  approve. Each role file now **denies** `Edit` and `Write` on both documents
  outright, and the architect — the one role that may change them — is
  blocked by `guard.sh` from doing it while a sprint is in flight.

How the hooks are connected:

| Event          | When                                     | Filter                                | Script               | Purpose                                    |
| -------------- | ---------------------------------------- | ------------------------------------- | -------------------- | ------------------------------------------ |
| `SessionStart` | On start, resume, `/clear` or compaction | Always                                | `session-context.sh` | Tell Claude where the project stands       |
| `PreToolUse`   | Before a tool runs                       | Commands, edits, writes and notebooks | `guard.sh`           | Block forbidden actions before they happen |
| `PostToolUse`  | After a tool runs                        | Edits and writes                      | `go-format.sh`       | Format and check the Go just written       |
| `Stop`         | When Claude is about to finish its turn  | Always                                | `stop-tests.sh`      | Do not let it finish with failing tests    |

A script answers with its exit code: `0` means "go ahead"; `2` means
"blocked", and its error message is sent to Claude.

### `hooks/guard.sh`

- **What it does:** before every command, edit, write or notebook edit, it
  blocks seven things:
  1. wiping the database (`docker compose down -v`, `docker volume rm` or
     `prune`, `make reset`), with a dry run (`make -n reset`) allowed;
  2. changing a migration that is already on `main`;
  3. committing on `main`, in a role session;
  4. writing the agent configuration — `CLAUDE.md` and `.claude/**` — in
     every role except the architect, which may write `CLAUDE.md` and
     `.claude/rules/` and nothing else;
  5. writing `docs/project-specs.md` or `docs/sprints-plan.md` from the
     shell, in every session including the developer's: a change goes
     through the `Edit` tool, in an architect or developer session. The path
     match is anchored, so an unrelated file such as
     `/tmp/x/docs/sprints-plan.md.orig` no longer trips it;
  6. the architect writing anything under `docs/` while a `sprint/*` branch
     is checked out. The design never moves under a sprint in flight;
  7. any tool other than `Bash` whose path it cannot read. Every non-`Bash`
     tool is treated as a path write, from `file_path` or `notebook_path`; a
     write-capable tool the guard cannot read is refused, not waved through.
- **Why:** a permission rule only compares text. This script can reason, for
  example by asking git whether a migration is already on `main` or which
  branch is checked out. It is also the floor under the permission files: a
  deny rule with a mistyped path silently allows what it meant to forbid.
- **Worth it?** Yes, essential. It prevents the most expensive mistakes:
  losing data, breaking the database history, or an agent widening its own
  limits.

### `hooks/guard_test.sh`

- **What it does:** runs `guard.sh` against ~50 payloads in a throwaway git
  repository under `$TMPDIR`, one per rule and per carve-out, and asserts the
  exit code of each. It prints `PASS` or `FAIL` per case and exits non-zero
  if any case fails. Run it from the project root:
  `.claude/hooks/guard_test.sh`.
- **Why:** the guard is a pile of regular expressions with the whole project
  behind it, and a hook that stops blocking fails silently — nothing tells
  you that the rule you changed now lets everything through. The tests are
  what let it be edited at all.
- **Worth it?** Yes. Run it after every change to `guard.sh`, and add a case
  with every new rule.

## 3. How the work is checked

### `hooks/go-format.sh`

- **What it does:** every time Claude writes a Go file, it formats it with
  `gofmt` and looks for problems with `go vet`.
- **Why:** Claude gets the error immediately and fixes it, without anyone
  asking.
- **Worth it?** Yes. Cheap and useful in any Go project.

### `hooks/stop-tests.sh`

- **What it does:** the builder cannot finish while
  `make test-short` fails.
- **Why:** it turns "the tests must pass" from a request into an obligation.
- **Worth it?** Yes, essential. It is the Definition of Done, enforced.

### `agents/go-reviewer.md`

- **What it does:** a second Claude, unable to edit, that reviews the code
  against Go conventions, specs §5 and the "Project rules" of `CLAUDE.md`,
  and returns a list of problems. A finding is blocking only if it breaks an
  acceptance criterion, an invariant or a project rule, and it must name the
  one it breaks; the category is a label for the kind of problem, not its
  severity.
- **Why:** whoever writes the code is not a good judge of it. This reviewer
  has not seen how the code was written.
- **Worth it?** Yes, essential. You can also call it directly:
  "Use the go-reviewer subagent on the uncommitted changes."

### `skills/audit-sprint/SKILL.md`

- **What it does:** audits a finished sprint and appends the verdict to its
  report, following section 2 of `.claude/templates/sprint-report.md`. Round
  1 is the full audit, checks A1–A10 of plan §4: it re-runs the
  verification, checks that each test really tests what it claims, and runs
  `go-reviewer`. After the builder's one fix round, round 2 has a closed
  scope — the verification again, every blocking finding of round 1
  resolved, and the files the fix touched breaking no criterion, invariant or
  project rule. Nothing else is reopened, and anything new it notices goes to
  the debt ledger.
- **Why:** it does not trust what the builder says; it checks it. The closed
  second round is what stops a sprint from being audited forever: there are
  two rounds, never a third.
- **Worth it?** Yes, if you work in sprints. It is half of the process.

The loop, in full: `/start-sprint NN`, `/audit-sprint NN`. `APPROVED` ends
it. `CHANGES REQUESTED` in round 1 sends it back to `/start-sprint NN`, which
runs the one fix round, then `/audit-sprint NN` again for round 2. Only two
things can make round 2 request changes: an unresolved blocking finding from
round 1, or a fix that broke something. That halts the sprint, and the
developer decides what happens next.

## 4. How the work is done

### `skills/design-project/SKILL.md`

- **What it does:** turns a design conversation into `docs/project-specs.md`,
  and nothing else. It argues with the developer instead of transcribing,
  stops once the specs are written, and invokes `/scaffold-project` only
  after they are approved. Invoked on a project already under way, it revises
  the specs in place and records every change in §14.1.
- **Why:** every later piece cites the specs by section number. If that one
  document is vague, the audit has nothing to check against and every sprint
  argues about what was meant.
- **Worth it?** Yes — or write the specs in a chat from the template
  instead. What matters is that the specs exist and follow the template; the
  skill is one way to get there, and the better one when the design is still
  open.

### `skills/scaffold-project/SKILL.md`

- **What it does:** reads the approved specs and generates everything
  downstream: `docs/sprints-plan.md`, `docs/sprints-debt.md`,
  `docs/reports/`, the "Project rules" of `CLAUDE.md` and the project
  requirement of `.claude/rules/repository.md`. Run again on a project under
  way, it regenerates only the sprints that have no report yet.
- **Why:** one generator, one direction. Derived files written by hand drift
  from the specs, and a plan that no longer matches them is a plan the audit
  measures the wrong thing against.
- **Worth it?** Yes, essential. It is what makes the specs the single source
  of truth rather than the first of several.

### `skills/start-sprint/SKILL.md`

- **What it does:** runs a sprint of the plan from start to finish: branch,
  tests first, code, verification, probes, report and commit. The report
  follows section 1 of `.claude/templates/sprint-report.md`. If the audit
  requested changes, it runs the sprint's one fix round instead and appends
  section 3.
- **Why:** it replaces copying prompts from a chat. The process lives in the
  repository, so anyone can run it.
- **Worth it?** Yes, if you work in sprints. It is the other half of the
  process.

### `templates/project-specs.md` and `templates/sprints-plan.md`

- **What they do:** the shape of the two immutable documents. The specs
  template is the contract for `/scaffold-project`: it marks which sections
  are required, because the generator reads them. The plan template is what
  `/scaffold-project` writes, and it carries the fixed parts of the process —
  the audit protocol, the test rules T1–T14 and the probe catalogue.
- **Why:** the skills cite both documents by section number. A renumbered or
  missing section breaks the citation silently.
- **Worth it?** Yes, essential. They are the reason a new project can start
  from a conversation instead of from a blank page.

### `templates/sprint-report.md`

- **What it does:** defines the exact shape of a sprint report in three
  parts: the initial report, an audit round and a fix round.
- **Why:** four pieces depend on that shape: `/start-sprint` writes it,
  `/audit-sprint` appends to it, audit check A10 verifies it, and
  `session-context.sh` reads it. One file keeps them in sync; change the
  format there and nowhere else.
- **Worth it?** Yes, if you work in sprints. Without it, a heading written
  slightly differently silently breaks the session context.

### `templates/sprints-debt.md`

- **What it does:** defines the debt ledger, `docs/sprints-debt.md`: one row
  per non-blocking audit finding, with its sprint, location and status.
  `/audit-sprint` appends to it in step 4b, and everything round 2 notices
  lands there.
- **Why:** a non-blocking finding is real, but not worth halting a sprint
  for. Without a ledger it is written once into a report nobody opens again,
  and never fixed.
- **Worth it?** Yes, if you work in sprints. It is what makes the hardening
  sprint possible: the list of what to clean up is already written.

### `hooks/session-context.sh`

- **What it does:** when a session starts, or after `/clear`, it tells
  Claude the current branch, the latest commits, and from the newest report
  its `## Summary` and every `**Verdict:**` line. It also warns when a
  session has no role on a `sprint/*` branch.
- **Why:** the conversation is cleared on every sprint, and the session needs
  to know where things stand before it reads anything. It stays short on
  purpose: the deviations and the open issues are in the report, and a
  session that needs them opens it. The warning catches the case where
  someone starts `claude` instead of a launcher, and every command is then
  denied without explanation.
- **Worth it?** Yes, although it is the least critical hook: if it fails,
  Claude still works, it just finds its way less easily.

### `roles/architect.json`, `roles/builder.json` and `roles/auditor.json`

- **What they do:** the permissions of each role. The architect reads the
  code and writes the documents, `CLAUDE.md` and `.claude/rules/`, but no
  code; the builder can build and test without asking; the auditor can only
  read, verify and write its verdict into the report and the ledger. The
  builder and the auditor deny `Edit` and `Write` on `.claude/**`,
  `CLAUDE.md` and both immutable documents, so an attempt on them is refused
  without a prompt — that is what probe P01 checks.
- **Why:** the auditor cannot touch the code, even if it tried, and a denial
  with no prompt cannot be approved by mistake at two in the morning.
- **Worth it?** Yes. The architect runs before sprint 00 and between
  sprints; the builder and the auditor run in two parallel terminals. With a
  single session doing everything, they are not needed.

### `bin/architect.sh`, `bin/builder.sh` and `bin/auditor.sh`

- **What they do:** start Claude with the right role, permissions and mode,
  so you do not have to remember any of it.
- **Why:** the role files do nothing on their own; something has to load
  them. These scripts always do it the same way.
- **Worth it?** Yes, they go together with the roles: remove one and the
  other is useless. One launcher per role, named after it.

How to use them, from the project root:

| Session     | Start                                           | Then run                                    |
| ----------- | ----------------------------------------------- | ------------------------------------------- |
| architect   | `.claude/bin/architect.sh` (before sprint 00)   | `/design-project`, then `/scaffold-project` |
| 1 — builder | `.claude/bin/builder.sh`                        | `/start-sprint NN`                          |
| 2 — auditor | `.claude/bin/auditor.sh` (on the sprint branch) | `/audit-sprint NN`                          |
